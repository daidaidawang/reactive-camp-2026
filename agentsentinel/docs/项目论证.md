# AgentSentinel 的项目论证

核对日期：2026-11-23。按已安装的 Web3 研究雷达方法整理。

## 观察到的问题

初版能发出订单与风险事件，但没有订单资金结果。保证金没有和待处理告警绑定，Agent 可以在跨链回调前提款。代码里全额罚没被描述成“风险可定价”，但没有费率模型、损失估计、承保人或赔付机制。README 也没有给出项目流程或复现证据。

这些问题影响的是演示结论是否成立。先补可验证的订单与保证金流程，再说明哪些叙事仍是假设。

## 目标用户与问题

假设用户是给 Agent 分配小额链上采购预算的项目方。要限制谁能花、向谁付款、每笔最多多少，并在明确违规后停止继续操作，保存可审查的处置记录。

这个用户假设没有经过访谈，也没有真实采用或付费数据。当前原型只实现固定商户 ETH 付款，不声称覆盖通用 Agent 操作。

## 链上部分为什么存在

预算、商户债权、保证金和身份状态都由合约保存，第三方可根据交易与状态核对资金去向。仅使用数据库无法提供同等链上资金约束。

但“需要链上约束”和“需要跨链自动化”是两件事。当前所有被保护资产都在 Sepolia，同一交易直接撤权更简单、延迟更低。Reactive 的作用是把独立的事件接收、规则处理和异步回调做成可复现流程；它增加网络费用、交付延迟和活性依赖。

真正支持多链权限同步，需要部署多个目的链执行器、以明确命名空间标识回执、追踪每条目的链的完成状态，并处理部分失败。本版尚未实现，不能把网络支持跨链等同于项目已经完成多链保护。Reactive 官方文档说明了源链、目的链和回调机制：[Reactive contracts](https://dev.reactive.network/reactive-contracts)、[Origins & Destinations](https://dev.reactive.network/origins-and-destinations)。

## 已有替代方案

| 方案 | 适合解决的问题 | 本项目需要说明的差别 |
| --- | --- | --- |
| 单链合约直接拦截并撤权 | 已知硬规则、状态都在同一链 | 本场景最简单的基线；不能宣称 Reactive 更快或更必要 |
| Safe 的模块与 Guard | 可编程账户权限及交易检查 | 不是所有 Agent 约束都需要新建钱包；本项目尚未集成 Safe |
| 普通链下监听器 | 自建事件监控与交易提交 | 部署方便，但监听器承担持续运行和签名职责；本项目默认规则路径不依赖 AI 服务 |

Safe 官方文档已有模块和交易前后 Guard 检查机制，也指出错误 Guard 可能锁住资金：[账户架构](https://docs.safe.global/advanced/smart-account-overview)、[Safe Guards](https://docs.safe.global/advanced/smart-account-guards)。本项目的差异是把证据、锁款、异步处置和失败恢复放在一个可演示流程里；没有证据支持“首创”或“全面优于现有方案”。

## AI 实际做什么

`amount > maxSpend` 是算术比较，不需要 LLM。模型仅根据结构化证据生成解释，便于人工查看。允许的处置等级只有 3，模型不能把超额降为无事发生，也不能扩大罚没金额。

规则模式默认开启。AI 解释模式会等待至多五分钟，之后任何人可以发交易触发兜底；“任何人可以”不代表链上会自行发起这笔交易。没有调用者时仍会等待，但源链已经停止该 Agent 继续下单并锁住保证金。

若赛道要求 AI 深度参与决策，这一版的 AI 创新程度有限。不能用“真实模型生成了一句理由”证明模型能够识别未知风险。

## 保证金的经济含义

全额罚没是一条公开、固定的演示策略，针对被拒绝的超额请求。它既不是损失赔偿，也不是保险定价。金额高低、误操作是否值得全额处罚、项目方是否会滥用授权修改，都还没有经济或用户证据。

实际试点前应考虑用户明确接受策略、申诉、比例处罚和治理延迟。当前没有这些机制，不适合托管生产资金。

## 可以怎样验证方向

| 待验证判断 | 最小验证动作 | 继续或缩小范围的条件 |
| --- | --- | --- |
| 项目方需要可验证处置记录 | 找实际维护 Agent 预算的人，复盘现有操作和异常处理 | 如果现有钱包限额足够，优先集成钱包，而不是新造执行入口 |
| 多链独立处置有用 | 两个目的链，用同一个违规证据触发各自撤权，模拟其中一个失败 | 只有确实需要多链协调时，继续扩展 Reactive 用法 |
| AI 解释提高可用性 | 同一批告警，对比规则文案与模型文案的理解时间、事实错误 | 若模型不能改善理解或引入错误，保留规则说明即可 |
| 异步流程可运维 | 实网记录源交易、Reactive 请求、目标回调的费用与延迟，主动制造缺费失败 | 未证明可恢复前，不宣称可靠交付或生产可用 |

研究新颖性尚未证明；黑客松可展示性来自完整证据和可重复故障演示；产品可行性需要真实用户场景；商业持续性目前没有付费或成本数据支撑。
